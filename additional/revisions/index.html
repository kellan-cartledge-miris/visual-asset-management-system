Version Details​

2.7.0​

Release date: 2026-11-20

Major changes:

  • Added the GenAI CAD STEP Agent pipeline, in which a Strands agent creates or modifies a CAD STEP file from a prompt, on Amazon Bedrock AgentCore Runtime or AWS Batch on Fargate.
  • Added the Video SOP/BOM Extraction pipeline, which transcribes one to four narrated teardown videos with Amazon Transcribe and derives a step-by-step SOP, an LCA-BOM-INPUT bill of materials, a lab summary, and verification key frames with Amazon Bedrock.
  • Fork extension points — A fork adds its own APIs, pages, CDK resources, permission object types, CLI commands, MCP tools and viewers in files upstream ships empty, and add-on code moves out of the core list files. (issue #456, issue #457)
  • Miris Spatial Streaming: The Miris Spatial Streaming add-on streams USD files uploaded to Miris in the file viewer, with each viewer key delivered by an add-on route only after VAMS authorizes the asset and checks that the Miris asset is bound to it, and the Miris upload pipeline uploads USD assets to Miris when they are uploaded to VAMS. (issue #TBD)

Breaking changes:

  • vamscli execution details-metadata is renamed to vamscli execution details metadata. execution details is now a group: execution details <id> still returns the whole detail view unchanged, and execution details metadata|files|results <id> page one part of it. Update any script that invoked the flat details-metadata form. (issue #858)
  • Every AWS Batch compute environment behind a GPU pipeline is replaced on update. The NVIDIA Cosmos, GR00T Finetune and Gaussian Splat compute environments are created anew on the AWS Batch service-linked role, their job queues are re-pointed automatically, and the previous environments are deleted. It is a single cdk deploy with no configuration change and no flags to set before or after, and every deploy after it updates those environments in place. Replacing the instances terminates any job still running on a GPU pipeline, so in-flight executions are allowed to finish before updating. An environment that names its own Batch service role cannot have its launch template, instance types, subnets or security groups updated in place — Batch permits those fields to be updated only for an environment using the service-linked role — which is why the replacement happens once rather than being deferred. See v2.6 to v2.7 update guide. (issue #813)

Added:

  • GenAI CAD STEP Agent pipeline — A Strands agent creates or modifies a CAD STEP file from a prompt, optionally researching the design online, running generated CadQuery scripts in a bounded subprocess (resource limits, process-group timeout that also ends a child that left the group, non-dumpable agent and init processes) with a bounded self-repair loop, and writing the STEP file, a report and the measured figures (volume, bounding-box size, solid, hole and fillet counts, units) as file attributes back to the asset, plus cadAgent* file metadata and the status and mode attributes when the run's WRITE_AGENT_METADATA tag is on (default off) and the outcome as a structured result on the execution; the geometry it inspects and reports is that of the file's solids, and annotation geometry outside them (the PMI planes and curves of an AP242 export) is counted, not measured, and does not travel into the output file; on a modify run the inspection names the thickness axis of a sheet-like part and every script result states what the attempt changed against the input (volume, hole and solid counts, bounding box; a volume difference within the part's re-export noise band is reported as such, with the band). Modify and generate templates with per-run tags (prompt, output name and prefix, research, model provider, OpenAI model id, attempt budget, agent metadata; a Bedrock run uses the deployment's bedrockModelId, and a run naming another Bedrock model is refused before it starts); Amazon Bedrock by default with an OpenAI provider through a Secrets Manager secret; an Amazon Bedrock guardrail with a prompt-attack input filter screens the instruction and every fetched page, and the page-fetch tool reaches public hosts only; deployable to Amazon Bedrock AgentCore Runtime (warm sessions, one run per session; a run that lands on a busy slot is retried onto it for up to about 7.5 minutes) or AWS Batch on Fargate (an execution abort stops the agent container; a run that reaches maxRunSeconds is failed and stopped), with the deployment waiting for the CodeBuild image build, whose Amazon ECR repository is encrypted with the VAMS KMS key when useKmsCmkEncryption is enabled (repository name ending in -kms). An in-repository evaluation harness scores the agent over a 36-case corpus on geometry, honesty and design intent (an Amazon Bedrock LLM judge with per-case rubrics), with golden diffs against reviewed reference parts. An asset bucket in another Region is supported on both runtimes: the container reads and writes each asset bucket in the Region the workflow manifest names. Every run writes the full set of file attributes and metadata keys it manages, with an empty value for a figure it did not measure, so a new version of a file does not keep an earlier run's figures. (issue #347)

  • Execution output types + on-demand file and result reads — Every workflow execution reports outputTypes, the subset of File/Metadata/Result it produced, on both executions lists (the global board and the per-asset Workflows tab), rendered as badges; no output content appears on the list. Two on-demand reads page a run's output on the existing /details/* family: GET /workflows/executions/{executionId}/details/files?collection=input|output (token-paged) and GET /workflows/executions/{executionId}/details/results (the concatenated result text, token-paged by a 5 MiB response budget). The web adds an Output Types column on both boards, a scrollable/copyable modal behind the Result badge that loads the result a page at a time and downloads it whole as a .txt file, and a details-page lazy re-fetch of any collection reported truncated. The CLI execution details becomes a group — execution details <id> is the whole view, with new metadata (renamed from details-metadata), files and results (--auto-paginate, the default with -o FILE) subcommands — and the MCP server gains page_execution_detail_files and get_execution_results. Pre-existing executions report outputTypes: [] with no migration. (issue #858)

  • Image to 3D pipeline — GPU-accelerated single-image 3D mesh generation aimed at turning one photograph into a printable mesh. Six open-weight models ship behind one pipeline and are chosen per run by template: Stable-X Stable3DGen (the default, and the only one with no NVIDIA-licensed dependency), Meta SAM 3D Objects, Microsoft TRELLIS.2, VAST-AI TripoSR, StepFun Step1X-3D and Tencent Hunyuan3D-2, beside a Blender agent path that builds or refines the subject in headless Blender, reasoning with the Amazon Bedrock model the deployment configures. Each configuration template groups its fields by the stage that reads them, in run order. A configurable print-readiness stage follows generation — a mesh repair ladder, hole filling, winding and normal repair, face-budget decimation, a fidelity guard that refuses a repair which would destroy volume, and a print gate that reports each failing criterion with its measured value. A model that produces geometry only can be given colour by projecting the input photograph onto the mesh, with the camera recovered by silhouette matching and reported with its confidence margin. Every output file carries file-level metadata naming the model that produced it and that run's measurements. Model weights are cached on a shared Amazon EFS filesystem with an Amazon S3 backup. Enable via app.pipelines.useImageTo3d; each model is enabled independently, and a HuggingFace token is required whose account has approved access to the gated repositories of the models it enables. The models carry different licences, and the TRELLIS.2 and Step1X-3D images are limited to non-commercial use by a transitive NVIDIA dependency — see Notices before enabling one. See Image to 3D and its stage, model and option reference. (issue #814)

  • Video SOP/BOM Extraction pipeline — A new pipeline transcribes one to four narrated teardown videos from one asset with Amazon Transcribe and derives a step-by-step SOP, a bill of materials in the 66-column LCA-BOM-INPUT layout, a lab summary, and verification key frames with Amazon Bedrock, running as an AWS Batch Fargate container. Two templates cover full and transcript-only runs, and three workload-profile templates apply the same stages to any narrated hands-on procedure (SOP, tools and materials, overview), construction site walkthroughs (walkthrough log, equipment list, activity log, site report) and narrated business processes (step list, process document, overview) through a template profile block of stage prompts, stage limits and extra artifacts; every template uses the deployment's one bedrockModelId, and RUN_VISUAL_VERIFICATION turns key-frame verification off. File-count and total-duration caps are deployment configuration, a refused run reports the active limit as a readable execution error, and a video set with no detectable speech is rejected. Enable via app.pipelines.useGenAiVideoSopBom (commercial and AWS GovCloud (US) partitions). An asset bucket in another Region is supported through the VPC's cross-Region Amazon S3 endpoint; an input in a Region without one is refused before the job starts. See Video SOP/BOM Extraction pipeline.

  • Video SOP/BOM scratch cleanup — The pipeline's end step deletes the run's pipelines/genai-video-sop-bom/<executionId>/ scratch objects on every failed, rejected, or unreported outcome after releasing the workflow task token (the container deletes them itself on success), with its Lambda role granted a list and delete on the auxiliary bucket scoped to that prefix root. Because the auxiliary bucket is versioned, the prefix's lifecycle rules also expire noncurrent versions one day after deletion and remove the expired delete markers, so a deleted scratch object stops being stored rather than remaining as a hidden noncurrent version.

  • External asset buckets in another Region — A bucket entry's bucketRegion may name any Region in the deployment's partition. For each such Region a <name>-xregion-<baseStackName>-<bucketRegion> stack deployed into that Region owns the bucket's S3 notification topics and notification configuration (and, with useKmsCmkEncryption, a regional key: generated, or the replica of an imported multi-Region mrk- key), and the deployment-Region SQS queues subscribe to those topics cross-Region. Every backend S3 call and presigned URL for an asset bucket is signed for the bucket's Region; the buckets-table rows carry bucketRegion and bucketAccountId, which GET /buckets, the web create-database bucket picker, vamscli database list-buckets and the MCP list_buckets tool show. Workflow manifests name the Region of every input file and of the output bucket; the Lambda-container pipelines and the VAMS-owned Batch containers (Splat Toolbox, Isaac Lab, NVIDIA Cosmos and GR00T) address each asset bucket in that Region, while ModelOps and RapidPipeline, whose third-party images read Amazon S3 themselves, are same-Region only and reject a cross-Region bucket before the job starts. The default asset bucket must be in the deployment Region. The four AWS Batch pipelines whose compute runs in isolated subnets (Potree viewer, 3D thumbnail, GenAI metadata labeling, coordinate transform) read a cross-Region input through the VPC's cross-Region S3 endpoint and reject an input from a Region without one before submitting the job, naming both remedies; the external S3 setup guide documents the per-Region stack, the regional key, the network variations and the procedure for moving a pipeline to private subnets when the endpoint is unavailable. (issue #410)

  • app.useGlobalVpc.addCrossRegionS3Endpoints — Default true in all three templates. With the VPC enabled and an asset bucket in another Region, the VPC builder creates one Amazon S3 interface endpoint per bucket Region (ServiceRegion set, private DNS, isolated subnets) so in-VPC Lambda functions and pipelines reach the bucket without internet egress; in the VPC a cross-Region copy is streamed because an S3 interface endpoint does not serve cross-Region CopyObject. Cross-Region AWS PrivateLink is commercial-only, so configuration validation rejects the flag outside the aws partition when a cross-Region bucket is configured. Creating the endpoint requires vpce:AllowMultiRegion on the deploying principal and each bucket Region must be CDK-bootstrapped. (issue #410)

  • External pipeline bridge integration surface — The resource-name SSM parameters gain an integration/* group (orchestration bus ARN, event source prefix, workflow state-machine role ARN) and lambdaFunctions/importGlobalPipelineWorkflow, so a pipeline bridge stack outside the deployment resolves the bus it registers on, the principal whose callbacks it trusts and the vamsSchema import function at its own deploy time. (issue #398)

  • app.pipelines.externalPipelineBridges — Each entry (accountId, roleArnPattern, optional invokeTargets) opens events:PutEvents on the orchestration bus to the roles matching the pattern through an aws:PrincipalArn condition on the bus resource policy, and adds the exact Lambda / SQS / EventBridge ARNs in invokeTargets to the shared workflow role. Configuration validation and the configuration builder reject wildcards beyond a trailing * on the role pattern, foreign partitions and a bare role/*; the list is empty in every template. (issue #398)

  • app.pipelines.executionLogReadPrefixes — The log groups the execution logs API may read from are configured as an allow-list of /aws/<service>/... names used verbatim as IAM resources; the default is the groups the built-in pipelines write to plus /aws/sagemaker/TrainingJobs, and *, /, /aws/* and anything outside /aws/ are rejected. (issue #398)

  • SageMaker sub-processes are abortable — A pipeline that registers a sageMakerTrainingJob (trainingJobArn) or sageMakerPipelineExecution (pipelineExecutionArn) has it stopped on abort and on workflow failure, and reported with live status in the execution details, in the deployment's own account and Region. (issue #398)

  • Sub-processes VAMS cannot stop are named — Every sub-execution summary carries abortable, the abort response lists such sub-processes under notAbortable beside warnings (a group abort lists each member's entries there with the member's executionId), and the execution detail view renders an unknown resourceType by its registered label and stage with a note that an abort leaves it running; the abort toast and board notice lead with a one-line summary of what was left running. vamscli execution abort --json-output carries notAbortable (and every other sibling of message) through, CLI mode summarises the left-running sub-processes on one line, and the MCP abort_execution tool forwards both arrays and describes what a non-empty notAbortable means. (issue #398)

  • Externally owned pipelines documentation — custom-pipelines.md describes the bridge pattern end to end (deploy-time SSM discovery, body and heartbeat contract, two-role trust with aws:PrincipalArn and sts:ExternalId, registration events, invokeTargets, the log-read allow-list and vamsSchema registration from a non-VAMS stack); the configuration reference and AWS resources pages document the new fields and parameters. (issue #398)

  • Compare-mode visualizers — The viewer plugin framework gains a compare mode alongside the visualize path. A compare-capable viewer declares a compareMode block (file-count window, same-file-versions vs different-files and cross-asset gating); a viewer that can only compare (the new Text Diff Viewer) also declares compareMode.compareOnly and is never offered on the visualize path — for one file or many. Compare is reachable from the search results multi-select ("Compare Selected"), the asset file manager ("Compare Selected Files"), the version-comparison Compare actions and a per-row Compare in the version file list (selected version vs latest), all hosted by the file viewer modal. (PR #301)

  • Mode availability — Every Visualize/Compare entry point is gated by the registered viewers: Visualize is offered only when a non-compare viewer admits the selection and Compare only when a compare viewer admits its file count, shape and types. The modal shows a single admitted mode without the toggle and a "no viewer for this selection" state when neither applies; the version file list offers Compare only for types a differ handles. A single viewed file whose type a differ handles offers the toggle as well (file viewer modal and single-file view page): Compare opens the differ on the viewed version against latest, and the differ's per-side picker selects any other version. (PR #301)

  • Text Diff Viewer — Diffs two text files (or two versions of one file, optionally across assets) with side-by-side or inline layout, line/word/character granularity, a line-number toggle, collapse-unchanged with a configurable number of context lines, syntax highlighting and dark-mode support. Each side is fetched and authorized independently and carries its own version picker. The diff library is loaded on demand so it stays out of the base bundle. (PR #301)

  • 3D preview thumbnail compute tiers — The 3D preview thumbnail pipeline runs each job on a standard tier (default 4 vCPU / 16 GiB, 1-hour attempt) or, for inputs at or above largeTierThresholdGiB (default 2 GiB), a large tier (default 16 vCPU / 120 GiB, 3-hour attempt), instead of every job at 16 vCPU / 64 GiB. The tier's vCPU and memory are configured under app.pipelines.usePreview3dThumbnail.computeTiers and validated against the AWS Fargate task sizes; a run's computeTier template field (auto, standard, large) can force a tier, and the container receives the chosen tier as VAMS_COMPUTE_TIER. The pipeline's state machine timeout is 4 hours and its registered task timeout 14,400 seconds. (issue #470)

  • Fork extension points — A fork adds net-new API routes, handlers, models, CDK resources (in their own CustomBuilder nested stack, with settings in infra/config/custom/customConfig.json), SSM resource names, feature switches, web routes, navigation, services and pages, CLI commands, constants and client methods, MCP tools and viewer plugins in fork-owned files that upstream ships empty and does not modify, so merging an upstream release does not conflict with them. Custom routes are served behind the VAMS authorizer and cannot be anonymous, and a route, resource-name key, feature-switch value, viewer ID, CLI command or MCP tool that duplicates a core one is rejected. (issue #456)

  • Constants lanes — common/addonConstants.py and custom/customConstants.py (shipped empty) extend the permission object types, the constraint fields and the upload deny lists, which common/constants.py builds at import as core + add-on + custom; an entry that breaks a rule fails the import with an error naming the file and the entry. (issue #456)

  • Extension permission object types — A registered type and its constraint fields are validated, evaluated and listed by GET /auth/constraints/permissionObjects like a core type, so a fork authorizes its own entities on their own attributes. An extension type grants nothing until a constraint allows it, even to the admin role. (issue #456)

  • Append-only upload deny lists — An add-on or fork can add blocked file extensions and MIME types; it cannot unblock a core entry. (issue #456)

  • Open objectType in the API spec — objectType in the constraint request schemas of VAMS_API.yaml is a name pattern with the core types in its description instead of a closed enum. (issue #456)

  • Extending VAMS in a fork guide — A developer guide page lists every extension point list by list (core, add-on and custom files), the permission object type and deny-list rules, the recommended naming conventions and the known limits, with a worked example covering each hook that registers its own widget object type and ships an inline constraint template; the permissions, API, architecture and developer pages describe extension object types, and the /add-api-endpoint, /add-pipeline and /generate-permissions agent skills gain fork notes. (issue #456)

  • Gaussian splat thumbnails on the CPU — 3D Gaussian splats (.ply, .compressed.ply, .spz, .sog, .splat, .ksplat, .lcc, .lcc2) get a coloured, transparent-background preview without a GPU; a .ply is recognised as splats, a mesh or a point cloud from its header. A captured scene's preview shows its core, with the background around the subject and oversized fog splats left out and a tilted ground plane levelled, and each splat is drawn as a flat disc with the coverage of its Gaussian. An XGRIDS .lcc or .lcc2 scene is read at one level of detail; for .lcc2 only that level's chunk files are downloaded, and each chunk file it names must be in the same asset. (issue #469)

  • More 3D preview thumbnail formats and the right way up — Previews are generated for .pts, .3mf, .off and .dae files and vertex-only PLY point clouds, Draco files keep their colours, and the up axis comes from the file's own metadata, so Y-up STL files and models that are long in depth no longer render on their side. 3MF and COLLADA files are parsed with DTDs and external entities disabled, and a file that places the same part many times is expanded only up to the triangle budget.     • New pipeline and workflow data model — Pipelines and workflows are database-scoped definitions with a typed executionConfig (one block per execution type — AWS Lambda, Amazon SQS, Amazon EventBridge, or AWS Deadline Cloud — replacing the loose userProvidedResource JSON string) and an admin-only systemConfig covering input-file arity, asset scope, metadata inputs, input-file filters, and template requirements. A template overrides its pipeline's input-file arity, asset scope, metadata inputs, and input-file filters, so one pipeline serves several conversion matrices. Bodies store inline and offload transparently to the artefacts bucket above a size threshold. See Building custom pipelines.

A pipeline reads its inputs, output locations, and asset identity from a resolved manifest, and asset, file, and database metadata arrive in one grouped envelope.

It mirrors the cross-field validation getConfig() enforces at deploy time and is a helper rather than a gate — cdk synth remains the source of truth. See Configuration builder. Key fixes:

The full list is in the repository CHANGELOG.md; these are the ones that change what a deployment or a script observes.

  • Uploads no longer report success for a file the server refused. Completion is where the API runs its validations, and a file it rejects is deleted rather than stored — but both the CLI and the web upload decided each file's outcome from whether their own Amazon S3 part uploads had finished, and neither read the per-file verdict in the completion response. vamscli file upload printed "Successful files: 4/4" and exited 0 for an upload that left nothing in the bucket for one of them; the web summary said "Upload completed successfully" for the same case. Both now reconcile against the response and name the reason the API gave.
  • A .previewFile. companion is no longer lost when several files are uploaded together. A companion is sequenced separately from the file it previews, and the API accepts it only if that base file arrives in the same request or already exists in Amazon S3 — so the companion's sequence must complete after the base file's. The intended ordering existed only as a comment: both groups were handed to a single concurrent gather, so on a live deployment between 2 and 6 of 12 companions per run were refused and deleted, varying run to run because it was a race.
  • Metadata schema validation no longer fails open. Schema conformance, the controlled-list check, the value-type-change guard, and the restrictMetadataOutsideSchemas prohibition ran inside a block that logged a warning and continued on any unexpected error, so a transient Amazon DynamoDB error turned a configured governance control off and answered 200 with off-schema metadata stored. A create, update, or delete whose validation cannot complete is now refused.
  • vamscli assets download no longer reports success for a download that fetched nothing. Files the API declined to issue a download URL for were skipped one by one, so a request in which every file was declined still reported overall_success: true and exit code 0 — an empty output directory presented as a completed download. The most common cause is an asset that is not distributable.
  • Every AWS client the backend builds now carries the adaptive retry configuration, so a sustained burst is smoothed client-side instead of surfacing as throttling on the caller's request. The audit writer was the sharpest case: its CreateLogStream sits under an account-wide quota and its failure path drops the entry.
  • Subscriber change notifications are delivered for assets whose name is long or carries a line break. The Amazon SNS subject was built from the asset name unbounded, and SNS refuses a subject of 100 characters or more or one containing a line break — so an asset name of roughly 70 characters or more made every version-change notification for that asset fail permanently while only logging.
  • Security: AWS WAF now logs requests durably to a CloudWatch log group with Authorization redacted; CloudFront responses carry Referrer-Policy: strict-origin-when-cross-origin and a Permissions-Policy (asset identifiers appear in the hash route, so a full referrer disclosed them to third-party hosts — an ALB deployment exposes no listener attribute for either header and cannot carry them); the HuggingFace token supplied in configuration no longer leaves a cleartext copy on the build host; and the asset export no longer writes token claims or the asset-links response body to its log group.
  • Accessibility: pinch-to-zoom and swipe-to-scroll work on touch devices again. The document root declared touch-action: none, and because a gesture's effective touch-action is the intersection of the values along the ancestor chain, that suppressed both gestures on every page.

Documentation:

  • CLI documentation consolidated into the official site. The complete VamsCLI reference — every command and option, authentication and profile flows, installation, automation, and a new CLI-specific troubleshooting section — now lives under the CLI section of the documentation site (cli/). The legacy in-repo docs under tools/VamsCLI/docs/ are deprecated; tools/VamsCLI/README.md retains basic installation and quick start and points to the official site. See CLI Getting Started.
  • New developer security reference. Breaking changes:

  • The workflow, pipeline, and execution overhaul breaks externally registered pipelines. A pipeline written against v2.5 does not run unchanged: it reads its inputs from a resolved manifest rather than from the invocation payload, an asynchronous pipeline returns an AWS Step Functions task token for the workflow to advance past it, and it registers its sub-processes and log locations so abort and log retrieval reach them. Registration moves as well — a definition is declared in a file-based vamsSchema bundle imported through the schema importer, and a pipeline is referenced by composite pipelineDatabaseId:pipelineId. The data migration reshapes stored definitions but cannot change a pipeline's code, so every externally maintained pipeline is ported with Migrating custom pipelines from v2.5 to v2.6. Deployments running only VAMS built-in pipelines need nothing beyond the update steps. The pipeline, workflow, and execution API is the overhauled shape and is not backward-compatible with the pre-overhaul endpoints.
  • Reading, aborting, or re-running an execution requires the operation's action on every asset the run read — each input file's asset plus each asset named as a metadata source — where earlier releases accepted any one of them for the global listing while requiring all of them for the details, so a listing could offer a row whose details then returned 403. A role scoped to a subset of databases stops seeing cross-database runs it could previously list and stops being able to re-run them; widen its asset and database GET constraints to cover the databases those runs span to restore the earlier breadth. An asset that has been permanently deleted is authorized on the database it lived in, so the history of runs against a deleted asset remains reachable; an archived asset is unaffected and stays authorized on its own record. See v2.5 to v2.6 update guide.
  • The API Gateway endpoint changes. The migration from HTTP API (v2) to REST API (v1) creates a new API Gateway identifier and invoke URL, so any client registered directly against the old endpoint must be re-setup — including the VAMS CLI (re-run vamscli setup) and any external integration or script that stored the API base URL. The web application reads the API base URL at runtime and keeps working. Every VAMS CLI profile stores the API Gateway URL it was set up against, including a profile set up through the Amazon CloudFront or ALB URL, so re-run vamscli setup <BASE_URL> --force for each profile. Existing config.json files must also move globalRateLimit, globalBurstLimit, and endpointType under app.api.apiGatewayRest and add app.api.apiType set to "APIGATEWAY_REST". See v2.5 to v2.6 update guide.
  • A VPC deployment that runs all Lambda functions in the VPC without VAMS-managed VPC endpoints now requires an AWS Systems Manager interface VPC endpoint. With app.useGlobalVpc.useForAllLambdas enabled and app.useGlobalVpc.addVpcEndpoints disabled, the operator must supply the SSM endpoint: every non-pipeline Lambda function resolves its resource names from Parameter Store at cold start and fails without SSM API access.
  • OpenSearch index names rolled forward to vams-assets-v3 and vams-files-v3. The schema-deploy custom resource creates the empty v3 indexes; the previous v2 indexes are abandoned and left in place until you delete them manually. A reindex is required to populate v3.
  • OPENSEARCH_VERSION switched from OPENSEARCH_2_7 to OPENSEARCH_3_5. Provisioned OpenSearch domains will perform a major-version engine upgrade. Serverless collections are unaffected.
  • OpenSearch Serverless now deploys the collection into a collection group and adds nextGen, allowPublic, enableStandbyReplicas, and OCU capacity options. Because the collection is placed in a collection group, the public-access network-policy change is applied, and the group generation (CLASSIC or NEXTGEN) is set, enabling or changing Serverless requires a re-deployment: disable Serverless and deploy, then re-enable with the new settings and deploy, and reindex. A minimum OCU of 0 requires nextGen=true, and nextGen=true requires enableStandbyReplicas=true (NEXTGEN collection groups do not support disabled standby replicas); a private collection (allowPublic=false) requires app.useGlobalVpc.enabled (only the OpenSearch-facing Lambda functions are placed in the VPC, so app.useGlobalVpc.useForAllLambdas is not required). See v2.5 to v2.6 update guide.
  • The authorizer claims context shape changed, which can break customized MFA, claims, and login-profile logic. Deployments that have edited the customization hooks under backend/backend/customConfigCommon/ must review them before upgrading; stock deployments need no action. The REST API (v1) REQUEST authorizer delivers claims as a flat map of string values under requestContext.authorizer, rather than nested at requestContext.authorizer.jwt.claims or requestContext.authorizer.lambda as the HTTP API (v2) did — so custom logic that branches on those nested keys and falls through to an empty dict now silently reads no claims instead of raising. Every value is a string, so JSON-valued claims (vams:tokens, vams:roles) need json.loads and vams:mfaEnabled is "true"/"false". Read claims through request_to_claims(event) instead of indexing the authorizer context directly. Additionally, customMFATokenScopeCheckOverride changed signature from (user, lambdaRequest) to (user, authorizerJwtClaims, lambdaRequest), is now called from the authorizer instead of each handler, and its Cognito default uses admin_get_user with the new USER_POOL_ID environment variable; a hook still written against the old signature is caught and defaulted to false, silently disabling MFA-gated roles. MFA is resolved once at authorization time and delivered as vams:mfaEnabled, so customAuthClaimsCheckOverride should read claims_and_roles["mfaEnabled"] rather than re-deriving it. See Authentication and Authorization Flow and Authentication Override Hooks.
  • Enabling a VPC-requiring feature (ALB, OpenSearch Provisioned, or any container-based pipeline) while app.useGlobalVpc.enabled is false now fails configuration validation with an explicit error instead of silently auto-enabling the VPC. Configurations that previously relied on the implicit auto-enable must set app.useGlobalVpc.enabled to true explicitly. See Configuration reference and Plan your deployment.
  • Provisioned OpenSearch availabilityZoneCount defaults to 2 and the VPC is built with that many Availability Zones. Earlier releases built the VPC across 3 Availability Zones for provisioned OpenSearch while the domain used only 2, so on upgrade the unused third AZ subnet is removed — a VPC downgrade that can fail subnet deletion when elastic network interfaces are still attached. Set availabilityZoneCount to 3 to preserve the existing VPC, or follow the drain-and-redeploy teardown to move to 2 AZs. See v2.5 to v2.6 update guide.
  • Role constraints that scope the pipeline objectType by pipelineType are no longer enforced as written, and a manual audit is required before upgrading. pipelineType is not a constraint criteria field in v2.6 — the value it held now lives in category — and a criterion naming an unrecognized field is dropped when the permission policy is compiled, so the constraint silently widens. See Permission constraint audit for pipelineType.
  • PUT /roles is a partial update, so a client that relied on an omitted field being reset must now send it explicitly. The endpoint previously rewrote description, source, sourceIdentifier, and mfaRequired on every request from the request model's defaults, so an edit naming only description set mfaRequired to false and nulled the source linkage — silently removing an MFA requirement, with nothing in the audit log to show it. Only supplied fields are written now, and clearing one is explicit ("mfaRequired": false, "source": null); description is always present on a role, so null is rejected. roleName is the only required field. POST /roles is unchanged.
  • An external-bucket-only deployment now requires an explicit default asset bucket. app.assetBuckets.externalAssetBuckets entries take a new isDefault field: at most one entry may set it, and exactly one must when app.assetBuckets.createNewBucket is false, or configuration validation fails at cdk synth. The default bucket is where a database created without an explicit bucket stores its assets, and where workflow execution inputs and pipeline outputs are written. A v2.5 config.json with createNewBucket set to false therefore needs one entry marked before it deploys.
  • AWS WAF changes from count-only monitoring to enforcement on a deployment with app.useWaf enabled. v2.5 ran the AWS Common Rule Set in count mode, recording matches without rejecting them; the three rule groups now declared in infra/config/policy/wafPolicyConfig.json are in block mode. A request that previously only incremented a counter is answered 403 by WAF before it reaches the authorizer or any Lambda function, so it produces no VAMS log entry to correlate with the upgrade. Two Common Rule Set rules are already overridden back to count because VAMS traffic trips them (SizeRestrictions_BODY for multi-part upload bodies, SizeRestrictions_QUERYSTRING for the presigned URL the SuperSplat viewer passes in ?load=). Review the WAF blocked-request metrics after upgrading; set "block": false on a group to return it to monitor mode.
  • CLI: bulk transfer commands now exit non-zero when any individual file fails. file upload, assets download, and assets export --download-files previously exited 0 after a partial — or total — transfer failure, printing a warning only a human reads, so a set -e script treated an upload that transferred 900 of 1000 files as complete. They now exit 1 whenever overall_success is false, and sync file push / sync file pull follow the same contract. Any job that branches on the exit code changes behaviour. Programmatic invocation is exempt: the industry commands call these through ctx.invoke() and read overall_success themselves.
  • CLI: profile info and profile delete exit non-zero for a profile that does not exist, and their --json-output shape on that path changed. Both previously exited 0. The response is now {"error": "…", "error_type": "ProfileNotFoundError"}; the success, profile_name, message, and exists keys are gone from the not-found path. The response for a profile that exists is unchanged.
  • CloudWatch log groups and the Isaac Lab training Amazon EFS file system now use the shared VAMS customer-managed AWS KMS key, and the EFS file system is REPLACED on upgrade. Applies only when app.useKmsCmkEncryption.enabled is true. The two resource kinds behave differently and only one loses data: a log group accepts the key in place, while an EFS file system's KmsKeyId is create-only, so CloudFormation replaces it and any cached training data on the old file system is not carried over.
Upgrade Path

Run the v2.5 to v2.6 migration at infra/deploymentDataMigration/v2.5_to_v2.6/upgrade after deploying the v2.6 stack. It runs seven steps by default (--steps all): reindex, assetHistory, workflowExecutions, auxPreviewRelocation, pipelineWorkflowDefinitions, globalListBackfill, and tagsNamespacing. Repopulating vams-assets-v3 and vams-files-v3 from source data is the reindex step alone — the other six reshape execution history, backfill asset history, relocate auxiliary previews, migrate pipeline, workflow, and tag definitions, and stamp the global-list partition attribute, so running only reindex leaves the rest of the upgrade incomplete. pipelineWorkflowDefinitions is the one step that is not safe to repeat. For provisioned deployments, if the OpenSearch 2.7 → 3.5 in-place engine upgrade fails during cdk deploy, deploy first with OpenSearch disabled in config.json to delete the existing domain, then re-enable and redeploy to create a fresh 3.5 domain before running the migration. See the v2.5 to v2.6 update guide for what each step does and the ordered procedure.

Known issues:

  • Two dependency findings remain in the documentation site, both reported against image-size, and neither has a patched version published upstream — every released version of the package is affected, so the findings cannot be resolved by raising the version. The package is a build-time transitive dependency of the Docusaurus MDX loader, which reads image dimensions while the static site is generated, and it is not part of the published site.
