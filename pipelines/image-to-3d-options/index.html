Image to 3D: Stages, Models and Options

A reference for choosing a path through the Image to 3D pipeline. Every run is the same ordered set of stages; what varies is which model generates the mesh, which stages are switched on, and what each one is tuned to. This page lays out the stages, the option each stage takes, which combinations produce colour, what each component is licensed under, and what has actually been measured.

For how the pipeline is built and deployed, see Image to 3D Pipeline. Every option named here is a template tag set on the execute form or in a configuration template's body.

What decides whether you get colour

Five of the six reconstruction models generate their own colour, and the Blender agent bakes a texture from the materials it authors. Stable3DGen generates none and can instead take colour from the input photograph. TripoSR, Step1X-3D and Hunyuan3D-2 can each be run with their texture stage off, in which case they too are geometry only. The Colour paths table is the short answer.

Stage map​

Each subgraph is one of the stages a template's form groups its fields under.

Three orderings in that map are load-bearing rather than incidental:

  • Per-vertex colour stays per vertex. glTF carries a colour array natively and exactly, and a renderer interpolates it across a triangle correctly, so the GLB the viewer reads is the colour the pipeline produced. A texture is built only for the OBJ, at export, once no further geometry will be added — an OBJ carries a colour array only through a non-standard extension that many readers ignore. That atlas is baked: the colour is rasterised into the charts an unwrap lays out, so neighbouring texels are neighbouring points on the surface. A colour palette — one texel per distinct colour, in deduplication order — is not something a renderer can sample, because a renderer interpolates the uv across each triangle and reads per fragment rather than per vertex. Measured on a 99,581-vertex mesh, 97.5% of triangles had their three corners more than eight palette texels apart, a median of 68 of a 184-wide palette, and 43% of rendered pixels came out badly wrong against the colour the mesh carried.
  • A preserved atlas is delivered by how the model laid it out. A contiguous atlas — a texture stage's own 2048x2048 output — ships intact, its unwritten texels flooded from the nearest written colour. A densely chart-packed one — the agent bakes thousands of small auto-unwrap islands with unwritten background between them — tears when a renderer samples across an island edge, so it is collapsed to per-vertex colour (resampledFromAtlas), read a texel and a half inside each of a vertex's faces and averaged, so a vertex on an island's border takes the island's colour rather than the border texel where the next island's bake margin bleeds in. A sample that lands on the atlas's cleared background — the bake writes nothing for an island narrower than a texel — is left out, and a vertex with no written sample takes the colour of the copies that meet at its position. Only the chart-packed model is collapsed; a per-vertex model (SAM 3D) never had an atlas, and a contiguous one is untouched. Because that leaves the agent's mesh with no atlas, the GLB export then welds the per-vertex splits the bake left behind — each merged vertex taking the mean colour of its copies — and recomputes smooth normals, so the viewer reads a smooth surface at a fraction of the vertices. A mesh that still carries an atlas keeps its uv seams split.
  • The rescale precedes the print features, because a feature's dimensions are millimetres of the printed object. With TARGET_SIZE_MM left at 0 the mesh keeps the model's own arbitrary scale and a millimetre dimension has no fixed meaning.

What projected colour can and cannot do​

  • It only touches a mesh that has no colour, so it can never overwrite a model's own appearance.
  • The view comes from the model, not the run. A reconstruction is written into a canonical frame keyed to the input photograph, so the view is declared per model (INPUT_VIEW_AZIMUTH, 0° for Stable3DGen) and only the tilt is searched. This matters because a silhouette search alone does not merely lose confidence on a near-symmetric subject — it can prefer a wrong view. Measured on a standing figure: it scored a view 225° from the correct one higher (0.838 against 0.776), and the colour that view projected landed the photograph's tones on the wrong parts of the body while every number the run reported looked healthy.
  • A model with no declared view falls back to searching, and reports what that search is worth. Step1X-3D has no calibrated view yet, so its projected runs report poseDecisive: false.
  • PROJECT_PHOTO_POSE overrides both, for a photograph not taken from the view its model expects.
  • It refuses rather than guesses when the best view scores below 0.35 intersection-over-union, when a mask guessed from the background colour covers more than 85% of the frame, or when the sample comes back a single flat tone.

How a template's form reads. Every field is labelled with the stage that reads it -- [1 Input], [2 Generate], [3 Cleanup], [4 Colour], [5 Print] and [6 Output], the subgraphs of the Stage map -- and the fields are ordered the way a run executes them, so the form reads top to bottom as the run does. A template shows only the stages its model uses: the SAM 3D Objects, TRELLIS.2 and Blender agent templates carry no [4 Colour] fields, because those paths bring their own colour. Each template's instructions end with a FORM paragraph that says the same.

Every template also carries PASS_THROUGH_INPUTS, off by default: a later pipeline in a workflow receives only the prior step's outputs, so a first step that must hand the photograph on copies it into its outputs beside the mesh.

A second pipeline and a two-step workflow. When the Blender agent is enabled, the deployment also registers genai-image-to-3d-refine, the agent's refine mode as a pipeline of its own on the same Lambda and images, and the workflow Image to 3D: reconstruct, then refine (genai-image-to-3d-refine), which runs the reconstruction pipeline and then the refine pipeline on one photograph. A workflow may not list one pipeline twice, which is why the refine mode is a pipeline of its own. Choose a first-step template that passes the photograph on, such as image-to-3d-sam3d-then-refine; the second step then receives the mesh and the photograph together, keeps the mesh's body, and projects the photograph onto it. Both pipelines also carry the two refit templates, so that step can run the scripted refit alone, or the refit and then the agent, in place of the agent alone. The same result is had by hand in two executions: run a reconstruction template, then the refine template selecting that output beside the photograph. Run end to end on the standing person -- SAM 3D then Astra -- this workflow produced the pipeline's most faithful person likeness so far, first of five in the blind round; the measured run is recorded with the Blender agent runs below.

Each template's instructions name the STAGES that model's run performs, which differ: Stable3DGen ends with the photograph-projection stage that supplies its colour, Step1X-3D and Hunyuan3D-2 each run a second texture stage of their own, and SAM 3D Objects, TRELLIS.2 and TripoSR carry colour out of the generate stage with the geometry. See Stage map for the shared sequence.

A template is registered only for a model the deployment enables, so the list an operator sees is the subset switched on in app.pipelines.useImageTo3d. Naming a template whose model is not enabled is rejected at execution.

Selecting one is optional on the execute form: the pipeline sets requireTemplate, and Stable3DGen is the default, so an execution that names no template runs that model. It also sets allowCustomTemplateOverride, so a caller may supply a configuration body of its own instead of naming a template — which is how an option that is deliberately absent from the form (see Per-model options) is set.

The pipeline takes one input file per run, filtered to *.png, *.jpg and *.jpeg, and reads no asset or file metadata. Its own outputs are written back as new files on the output asset, each carrying the file-level metadata described in What each output carries.

vamscli pipeline template list -d GLOBAL -p genai-image-to-3d
vamscli pipeline template get -d GLOBAL -p genai-image-to-3d -t image-to-3d-step1x3d

Off-form: SAM3D_CONFIG_RELPATH — the pipeline configuration path inside the gated weights repository — the interior-fill opening and the field dump above. Upstream's mesh postprocessing and texture baking are both declined, because both rasterize through nvdiffrast, which this image does not carry; the model is asked for vertex colour instead.

SAM3D_SOLID_INTERIOR is on by default. Off, the raw mesh is a closed outer shell with a second, inward-facing wall a few voxels inside it: the model's mesh extractor seeds every vertex of its grid that the sparse structure does not carry as outside, and that structure is a band around the surface rather than a filled volume, so the field reads outside, inside and outside again across the band and then outside through the whole interior; a wall is emitted at each sign change, sealing a void inside the object that the cleanup ladder then has to resolve. The mesh is watertight and one body, so every gate criterion accepts it and no exterior view shows it; the shell descriptors under BENCHMARK_REPORT are what do. On, the driver floods the grid from its boundary through its positive vertices, marks the positive vertices the flood cannot reach as inside wherever the outer skin encloses them, and hands the field back to the extractor, which emits the outer surface alone. The outer face stays where the model put it, except across the narrow gaps the fill closes, described below. The space beyond the grid counts as outside, so a reconstruction standing on a face of the grid keeps the floor under it. The flood runs through the positive field eroded by SAM3D_SOLID_INTERIOR_OPENING vertices and its reach is dilated back by the same amount, so a puncture in the model's inner layer up to twice that opening wide does not let the flood pour into the interior; an exterior gap that narrow is shut out of the flood in exchange, and a puncture wider than that leaves the interior as the model wrote it. The widest puncture differs from one reconstruction to the next, so under auto the driver grows the radius from zero, up to six, and reads each step's growth in filled vertices against the number of vertices the reconstruction carries: sealing a crease fills a sliver, sealing the inner layer fills a volume. The search ends at the first step after a seal that does not seal, and the radius settles on the last of the consecutive steps that filled at least six percent of them, or on zero when no step does, so an inner layer the opening cannot close is left as the model wrote it rather than bridged ever wider in the attempt.

What the flood leaves unreached is then read against the outer skin, the part of the surface that straight rays from beyond the grid reach along at least six of the 26 lattice directions. The skin's winding number, solved over the grid by FFT, is near one inside the skin and near zero outside it, and an unreached vertex below one half is handed back to the outside: a gap the outside sees into — between two legs, behind an ear, at the root of a handle — stays open, while an interior the skin encloses stays filled whatever the model wrote there. A narrow gap the skin covers stays filled too, and the mesh carries a flat, stair-stepped plate across its mouth: behind a strand of hair or a strap lying against the face, or along a groove under a body. Of what remains, the largest connected piece is the interior, and any other piece touching the outside is the mouth of a gap and is handed back too, unless its mean winding is at least 0.9 with at most a quarter of its vertices touching. A sealed puncture therefore settles one layer in, as a dent the width of the hole. Each filled vertex takes the negative of its own value, so a band vertex that held a small positive value crosses zero where the model's surface already was, and a vertex the hand-backs cut off from the outside is filled after all, so the field seals no void. Each end of a new crossing that the sparse structure does not carry takes the colour of the nearest vertex it does carry, rather than the mid grey an uncarried vertex decodes to.

A run with the option on stops rather than deliver the double wall if the upstream extractor is not where the driver expects it. Every run, on or off, writes sam3d_stats.json beside the mesh — what the fill did to the grid, the raw and exported mesh sizes, how many exported vertices carry that mid grey, the sampler values the pipeline resolved to, the GPU that ran and the upstream revision it ran — and it reaches the execution as the agent/sam3d_stats.json diagnostic and, compacted, as sam3dStats in the report's generation notes. With SAM3D_DUMP_FIELD on, the grid is written before the fill touches it, so the file holds the model's own field whether or not the fill ran.

The refit modes. BLENDERAGENT_MODE is set by the template rather than on the form, and chooses what a run does: agent, the agent alone, as described here; refit, a fixed chain of Blender steps with no agent and no model call; or refit-agent, that chain and then the agent refining its result. The refit takes ONE existing mesh and the photograph it was made from, and bl_refit.py runs it a step at a time. A refit run whose input files lack the mesh or the photograph is refused before an instance is provisioned, as is a BLENDERAGENT_MODE other than these three. It joins the mesh into one body and turns it to the view whose outline best matches the photograph's cutout, searched over azimuth in 15° steps at elevations of 0°, 15°, -15° and 30°. It rebuilds the surface if asked, then warps the mesh in the photograph's plane until its front outline matches the cutout, moving no part more than 3% of the subject's height and leaving depth alone. It raises and lowers the photographed side where a MoGe-2 depth estimate of the photograph shows relief the reconstruction smoothed away, fading towards the outline and held back wherever the surface would cross itself. It brings the mesh to TARGET_FACE_COUNT, removes loose fragments, fills holes, turns the faces outwards, and projects the photograph onto the side it shows, keeping the reconstruction's own colour everywhere else. When the registered view's outline matches the cutout at an IoU under 0.5, no searched view shows the photograph's subject, so the outline fit and the relief are skipped. Each step records what it measured, did and skipped in refit_report.json, attached to the execution with the outline before and after drawn over the photograph's.

The refit reads the subject's outline from the cutout, so a photograph that reaches it with no transparent background -- BACKGROUND_REMOVAL=none, or IMAGE_CLEANUP=skip on an opaque photograph -- is refused before Blender starts, naming BACKGROUND_REMOVAL. With several photographs the refit uses the first, and in refit-agent the agent sees them all. refit-agent checks the agent's settings before the refit starts, hands the agent the refitted mesh as its starting mesh, wearing the reconstruction's colour on its vertices as any refine's starting mesh does, beside the refit's own baked result (refit/refit.glb), its report, its outline pictures and the mesh it started from, and delivers the refit's result when the agent fails, with the failure in the run report. Its workspace also holds bl_refit.py, which the instructions tell the agent not to run on its scene. The refit's options are on the two refit templates only:

Inputs. One to eight photographs, plus optionally ONE existing mesh (.glb, .gltf, .obj, .stl, .ply) to REFINE rather than build from scratch -- which is how this stage runs after another model: select that model's output alongside the photographs it was made from. Photographs named front, left, back or right tell the agent which side it is looking at. A mesh with no photograph is accepted for a tidy-up without a reference. Every other model is REFUSED a mesh, at the Lambda boundary, before any GPU is provisioned.

What the agent receives is a fresh workspace holding the photographs as supplied and as cutouts, the starting mesh if any, a brief with the mode and budget, thirteen tools and an instruction document. Eleven of the tools are Blender-side: import a starting mesh; build a silhouette base -- a closed body whose front outline is the photograph's, inflated to a depth, with the photograph projected on its front and the outline's own edge colours on its back and sides; reshape the depth or width of a horizontal band; render from fixed orthographic views with each render's and each reference's mean colour named; inspect bodies and closedness; solidify the parts into one closed body with the colour baked across; bake a single object's material; project the photograph onto any one mesh, which is how a reconstruction model's body gets the photograph's face and clothing; write the mask of the atlas texels the camera never saw; render the current texture from a fixed view with a mask of what the photograph never covered, and bake an image model's completion of it back; export with re-import verification. agent_image_edit.py reaches an image model on Bedrock through the pipeline (below). And agent_gate.py is the pipeline's own judge: plain Python that imports the pipeline's gate, shape-descriptor and silhouette code and runs them on the agent's export -- pass or fail, bodies, height/width beside the photograph's, front silhouette IoU, which horizontal bands are too narrow or too wide and by how much, whether the model faces -Y, colour per band in words. The method is: audit the references, take the silhouette from the photograph, shape the depth, add what projects, match materials, solidify, export, measure, and finish only when the measurement says so. Completion is a set of FILES -- output/model.glb and a DONE.json carrying the measured numbers -- and complete is allowed only with the gate passed and a front IoU of 0.85 or better; the stage checks for the mesh rather than believing the final message.

How it is confined. Codex runs its commands in its own sandbox in workspace-write mode with the default /tmp carve-outs switched off, so the only writable location is the agent's workspace, which sits outside /tmp deliberately -- the pipeline's own directories live there. Its commands have no network. The workspace is wiped before every run. Credentials are excluded from the environment its commands see; the model is reached by the Codex process alone, through a loopback bridge that calls Bedrock on the task role. The sandbox mode is fixed, and no run option widens it.

How it reaches an image model. The photograph covers the surface the camera saw and nothing else, so the back and the sides of a projected model carry the colour of the nearest outline, which is flat. GPT-6 Astra produces text, not images, so it directs an image model rather than painting itself: once the model is one body with a real atlas, bl_view_fill.py renders its current texture, unlit, from one of the fixed views and writes a mask of the visible surface the photograph never covered; agent_image_edit.py asks a Stability AI model on Amazon Bedrock -- structure-guided regeneration, inpainting, search-and-replace, recolouring, style transfer, erasing -- to complete that picture with a prompt describing the subject from that side (the structure-guided model keeps the render's outline and pose, where an inpainting model given a mask over most of a figure redrew the figure); and the same tool bakes the result back onto exactly the faces that view saw, depth-tested, marking them so the next view fills only what remains. bl_uv_mask.py still writes a mask of the atlas texels the camera never saw, for a patch fixed in the atlas itself. The agent's commands still have no network: the tool writes a request file into requests/ and a broker in the pipeline process serves it with the task role, confines every path to the workspace, allows only the listed operations, runs the model through its us. inference profile, and writes the result back, with every pixel outside a mask returned as it was. The agent is told to look at each result and keep it only if it beats the flat colour, and the gate tool's SEAM lines -- the camera-facing colour against the rest, band by band -- are how it checks the join. For fine corrections the atlas is a PNG it edits with numpy from a Blender script.

How the model is reached. Codex speaks only the OpenAI Responses API; Bedrock exposes OpenAI-compatible Chat Completions and nothing else. A LiteLLM proxy inside the container bridges the two on loopback and calls Bedrock's Converse API with the task role's credentials, so no API key is minted or stored. The model id is deployment configuration (bedrockModelId); the commercial template carries the GPT-6 Astra cross-Region inference profile, and the runs recorded below name the model each used.

A new model id is not only a setting, though, and the first Astra runs showed why. The bridge library decides which request fields a Bedrock model accepts by looking the id up in its own model map, and silently drops anything it decides is unsupported; an id it has never seen therefore gets no tools, and the agent answers in seconds that it has no terminal. It also recognises an OpenAI model on Bedrock by the substring openai.gpt-5 in the id, so a gpt-6 id was sent Anthropic's thinking field and rejected by Bedrock before the first turn. The bridge hook registers the configured id from its nearest known sibling and widens that detection to any openai.gpt-<digit> id, so the id really is the only change. Measured before this was built: GPT-5.6 Terra through that bridge read an image, called a function tool, took the tool result, and streamed with high reasoning effort, which is every shape Codex uses.

One shape needed help, and the first live run found it. The agent's view_image tool returns the image it looked at as the tool call's result; the bridge translates that into a Converse tool result carrying an image, and the OpenAI models on Bedrock reject exactly that -- "This model doesn't support the image field for user messages" -- while accepting the same image beside the tool result in the same user turn. Measured across every placement a mid-conversation image can take: only the image inside the tool result fails. A pre-call hook on the bridge lifts image parts out of any tool output into an adjacent user message, which is the accepted shape; the agent looked at its first render and the run died before the hook existed.

What each run leaves behind. Beside the run report on the execution: the agent's notes, its brief, its build scripts, its self-assessment with known deviations, and an index naming where the rest went. The renders and the full event transcript go to the auxiliary prefix, because the workflow reads everything beside the report as text onto the execution record, and a PNG or a half-megabyte transcript there fails the run after the model has been delivered. Read the notes and the deviations before reading the mesh.

Reconstructing from several views​

One template takes more than one input file: image-to-3d-hunyuan3d-multiview. Hunyuan3D-2 ships a multi-view checkpoint whose image processor maps named views onto view indices and conditions a single reconstruction on all of them, up to four. Every other model here takes one image, and a run that supplies more to one of them is refused rather than reconstructed from whichever file came first — a reconstruction from one of four supplied views is a wrong answer that looks like a right one.

Name each file for the view it shows. Each input file's name must contain exactly one of front, left, back or right — cat_front.png, cat_left.png, and so on. A front view is required.

Rejected before any GPU workBecause
A filename naming no viewThere is no way to place it, and guessing places the subject's faces wrongly
A filename naming two views (front_left.png)Genuinely ambiguous
Two files claiming the same viewOne of them would be silently dropped
A set with no front viewThe texture stage is conditioned on the front view alone
More than four filesUpstream's processor knows four view indices

Assignment is by filename and not by the order the files are selected. Position looks simpler and is a trap: the ordering is whatever the manifest or a directory listing gives, back.png sorts before front.png, and an operator who lists the views in a different order would get a confident reconstruction of a rotated subject with nothing anywhere to indicate it. A filename carrying its own view is self-describing and cannot be silently misordered.

What extra views change, and what they do not. They condition the SHAPE stage, which is where a single photograph loses what it cannot see — a raised tail, a limb behind the body, the back of a head. They do not change the texture: the painting stage is conditioned on the front view alone, which is upstream's own behaviour, so the back of a multi-view subject is still painted from its front. Every view goes through the same background removal and framing, because a model conditioned on several views reads them as one subject seen from several places, and framing one differently describes a subject that changes size between views.

The multi-view checkpoint is a separate set of weights (tencent/Hunyuan3D-2mv) from the single-view one, and the input count selects it rather than a setting — the two must agree, and an operator cannot see the coupling. Both are pre-fetched, so a single-view deployment caches the multi-view weights once too; the alternative is an un-retried download during the first multi-view run, on the shared filesystem that has failed three times mid-write.

What each output carries​

Every exported mesh is stamped with its own metadata, so a file in an asset alongside meshes from other models still says which model produced it, whether it carries colour, and what the run measured — without opening the execution. IMAGE_TO_3D_MODEL, IMAGE_TO_3D_MODEL_LICENSE, IMAGE_TO_3D_COLOUR_IN_FILE, IMAGE_TO_3D_SOURCE_IMAGE_NAME and, when BENCHMARK_REPORT is on, the instance type, GPU, per-stage seconds and fill ratio. The full list is in Metadata applied to each mesh.

IMAGE_TO_3D_COLOUR_IN_FILE is worth singling out: it answers "does this file have colour", which is a different question from IMAGE_TO_3D_TEXTURE_STATUS. A run whose mesh is textured still writes a colourless STL, so the two disagree for that file by design.

What the execution carries​

The run's own report — the print gate's verdict with every measured value, the print features added, what the projection recovered and its confidence, and, when BENCHMARK_REPORT is on, the per-stage seconds, instance type and GPU — is written where the workflow reads it onto the execution, so it is read against the run that produced it rather than as a file in the asset.

That matters when several models write to one asset. A report describes a run, and asset-level metadata is singular: kept there, each model's run would silently replace the last one's report. On the execution each run keeps its own, including a run that the print gate rejected — a failClosed rejection writes no mesh but still reports every criterion it failed and by how much.

Per-file metadata is a separate thing and stays on the file: that is what identifies which model produced a given mesh, and it survives alongside meshes from other models.

Where a run's outputs land​

Each run writes into its own folder on the output asset, named {date}-{unixSeconds}-{executionId} — for example 2026-08-28-1788020396-0123456789abcdef0123456789abcdef. The workflow supplies that name through its defaultOutputFileBaseExecutionPathExtension, so an execution that names no output path of its own gets one folder per run rather than sharing one.

Each part earns its place. The date is readable at a glance and the seconds sort chronologically, which is what makes a run identifiable without opening it. The execution identifier is what makes the name unique: several models launched together can start within the same second, and because every model writes the same filenames — {stem}.glb, {stem}.obj, {stem}.stl — a folder shared by two runs means the second overwrites the first. There are no colons, so the folder survives a path-preserving download on any filesystem.

The folder says when; the file metadata above says which model. Together they identify any mesh in an asset holding output from several models and several runs.

Choosing which object to reconstruct​

The three salient-object backends — rembg, birefnet, rmbg2 — decide for themselves what the photograph is of. On a frame holding one subject that is what you want, and on a frame holding several they pick one with no way to ask for another. sam is prompted instead: it segments whatever SAM_PROMPT names, so the object to reconstruct is a per-run choice.

SAM_PROMPTMeaning
centre (default)A point at the middle of the frame, which is where a framed subject sits
x,yA point. "The object here"
x0,y0,x1,y1A box, as two opposite corners. "The object within this" — the stronger prompt where objects overlap, because it bounds the answer as well as locating it

Coordinates are fractions of the image between 0 and 1, not pixels, so one value keeps its meaning if the photograph is re-exported at another resolution. A prompt the pipeline cannot honour is rejected rather than replaced with the centre: the prompt exists to name one object among several, so silently ignoring it would produce a confident reconstruction of the wrong one. A resulting mask covering more than 90% or less than 0.1% of the frame is likewise rejected, since a prompt that landed on the background segments the background and every print-gate criterion then passes on a reconstruction of a wall.

warning
sam and rmbg2 are not available on every model

Both load their weights through transformers, and each model image carries its own. TRELLIS.2 and Stable3DGen pin one, SAM 3D Objects and Step1X-3D receive one transitively, and TripoSR's is older than SamModel needs — selecting either backend on a TripoSR run raises rather than falling back. That version cannot simply be raised for every image: TripoSR's own checkpoint carries the older transformers ViT module naming, so a newer release makes its weights fail to load and every TripoSR run fail. rembg, birefnet and none work everywhere.

sam returns a hard-edged mask. There is no graded alpha through hair or thin structure, where rembg and birefnet both produce a soft matte — measured on a studio photograph of a person, BiRefNet carried 5,781 pixels of partial alpha and a SAM mask carries none by construction. So sam is the backend for selecting an object, not for a difficult edge.

On an easy photograph the backend choice does not matter. Carrying a texture across the mesh cleanup​

Every cleanup operation — decimation, the repair ladder, the reconstruction rungs — hands back geometry alone, so a model's uv atlas has to be carried onto the new topology. The three ways of doing that differ by a factor of five, measured against the model's own untransferred output: a run with MESH_CLEANUP=false ships the atlas exactly as the model made it, which is ground truth with no transfer in it at all. Each carried result is then rendered from the same four viewpoints as that ground truth and compared pixel by pixel over the silhouette.

Subject: the photograph of a person. TRELLIS.2 at its full 984,382 faces decimated to the default 200,000 face budget — a five-to-one reduction.

Copying uv values is unsound rather than merely lossy. A uv is a coordinate into a discontinuous chart layout, so the nearest pre-cleanup vertex's uv is not an estimate of a new vertex's uv — two adjacent vertices legitimately sit in unrelated islands of the atlas, and the triangle between them sweeps across whatever the packer put in between as it interpolates. On the same meshes, 51% of TRELLIS.2's faces and 49% of TripoSR's ended up with a uv edge spanning more than a tenth of the atlas.

Re-baking asks the question that has a correct answer: which point on the model's original surface is this cleaned vertex, and what was the uv there. Because the answer comes from a triangle rather than from the nearest surviving vertex, it stays correct where decimation has moved a vertex further than the gap to a neighbouring surface — the case that otherwise paints one body part with another's colour. The uv it reads is then inset a texel toward its triangle's centre, because a decimation keeps the silhouette and so leaves its surviving vertices sitting on the original creases and chart borders, where a filtered read reaches into the neighbouring chart.

A cleaned face whose three original uvs land in different charts is the one case interpolation cannot serve, and it is common — 42% of faces on this subject, because welding a uv seam leaves one cleaned vertex standing where two original vertices sat in two charts. Such a face is shaded flat from its own centroid, which is interior to the face and so unambiguous. Shading it from its corners instead is what left a scatter of dark flecks over an otherwise correct result: every one of them sat on a face of this kind, and the source atlas was dark where its corner's uv landed while the surrounding surface was twice as bright. Measured on a repair-only cleanup, where no decimation runs and so every surviving vertex is a chart corner: 2.6% of pixels badly wrong from the corners, 0.25% from the centroid, with face-region detail moving from 2.64 to 3.04 against ground truth's 3.12.

Where a path currently stops​

  • Step1X-3D with texture on does not fit the general fleet as the model ships it. It was killed first by the container's host memory limit and then, with more, by CUDA out of memory on the 22 GiB L4 it landed on — upstream's own table puts geometry plus texture at 27 GB. Because AWS Batch places a job on vCPU, container memory and GPU count and cannot be asked for GPU memory, the model is routed to a compute environment restricted to g6e instance types, whose L40S carries 48 GiB.

  • That fleet has no capacity in this account, and a second compute environment does not rescue it. Every attempt to place a job on g6e returned InsufficientInstanceCapacity for g6e.2xlarge in us-west-2a and us-west-2b, across two generations of the environment and a widened instance list, and the job sat RUNNABLE. Listing the general environment second on that queue looks like it should rescue the job and does not: AWS Batch treats insufficient capacity as a transient condition on the first environment rather than as "cannot place", so it keeps waiting there. Step1X-3D therefore runs on the general fleet, and its texture stage is asked to fit that fleet instead — see STEP1X3D_TEXTURE_LOW_VRAM. The routing mechanism is kept and switched off, so a deployment in a region with g6e capacity can turn it back on with one entry.

  • Making the stage fit is preferred to chasing the card, and VAE slicing alone is enough. Upstream never calls the memory controls its own diffusers pipeline provides, so STEP1X3D_TEXTURE_LOW_VRAM applies one: VAE slicing, which splits the decode where a 2048x2048 output puts its largest allocation. The textured stage completes on a 22 GiB card in 335 s of the generate stage against 123 s for geometry alone, so the texture stage roughly triples generation and needs no larger card.

    The other two controls both break this model, in different ways, and neither announces it. Attention slicing replaces the custom attention processor its adapter lives in — see the next entry. Component offload leaves the processor in place but raises inside it during the forward pass, in upstream's own step1x3d_texture/models/attention_processor.py, because the adapter holds learned weights upstream places on the device itself and the offload hooks do not know about them. Installing the hooks succeeds, so the failure lands later and the texture is lost while the geometry export stands. That incompatibility was invisible for as long as attention slicing was also applied, because slicing had already swapped the adapter for a built-in processor that offload handles. So auto selects slicing at any card size.

  • Attention slicing must never be applied to this pipeline, and applying it produced an atlas of the wrong subject. Upstream builds the texture stage around a custom attention processor and loads learned weights into it — init_custom_adapter(self_attn_processor=DecoupledMVRowColSelfAttnProcessor2_0) then load_custom_adapter(..., "step1x-3d-ig2v.safetensors"). That processor carries both the reference image conditioning and the coupling that keeps the six generated views consistent with each other.

    Attention.set_attention_slice in diffusers finishes with an unconditional self.set_processor(SlicedAttnProcessor(...)). It checks nothing about what is already installed and has no preservation path; set_processor logs that it is removing "possibly trained weights". So enabling attention slicing replaces the adapter, and the stage samples SD-XL with neither the reference image nor any cross-view attention. What it wrote was content from the model's prior: an atlas holding several different pairs of jeans, a teal top, a pink top and red hair, on a subject wearing one black top and one pair of jeans — and, given the original photograph rather than a cut-out, a framed picture of a shoe and a monitor showing a user interface.

    With the call removed the same configuration produces a clean likeness — correct face, correct black top, correct denim on all four sides — and it is the strongest textured result of the five models.

  • Why a settings sweep could not find that. Six runs varying one thing at a time all produced an unrelated collage, which read as evidence that none of those settings was the cause. They were not, but the sweep could not have succeeded: attention slicing was applied in every memory mode that produced a texture at all.

    Every textured run made while the call was present had the adapter destroyed before inference, so each variant changed which content the prior produced without ever restoring the conditioning. The lesson generalises past this model: when a sweep of every available setting changes the symptom without fixing it, the fault is upstream of all of them, and reading the code the pipeline actually runs is cheaper than another round. Tracing upstream at the pinned commit settled it; two candidates were discarded on the way, since the call signature matches upstream's __call__(image, mesh, remove_bg, seed) exactly and upstream's export-then-reload of the geometry mesh between stages is not a frame conversion — a trimesh GLB round trip is identity, measured.

  • The geometry stage itself has failed once on the large card. On g6e, upstream's volume decoder raised torch.cat(): expected a non-empty list of Tensors — it produced no occupied voxels to decode — where the same configuration on an L4 succeeded twice. One occurrence, not yet attributed: the image's torch version is unpinned, so two builds of it are not necessarily the same image.

  • The weight-cache stage cost minutes on a warm cache, and no longer does. It was never deciding that present weights were present: the shared filesystem was not mounted, so every run restored the whole cache from Amazon S3 onto the instance's own disk and uploaded it again afterwards, and the times scaled with cache size rather than with anything about the check. Measured after mounting it and asking the check about the run's own model repositories: 101.5 s to 0.0 s, confirmed across two different instance types, so the cache is shared rather than merely warm.

  • A cold weight download onto the shared filesystem has failed mid-write three times. Each was OSError: [Errno 116] Stale file handle while a multi-gigabyte blob streamed into the cache — twice with concurrent jobs fetching one repository, once on a job running alone — and one of them left a partial blob that a later resume read as valid, corrupting a neighbouring model's weights. The cache stage now fetches a missing background-removal repository itself rather than leaving transformers to download it lazily from inside preprocessing, and every fetch retries on that fault, discarding the partial download rather than resuming into it. What this does not do is make the shared filesystem reliable under a long write; it makes the failure recoverable and keeps a corrupt resume off the cache.

  • Hunyuan3D-2 has never run. It is wired as a sixth model path and carries no measurements, so nothing on this page ranks it. Two of its per-model constants are also uncalibrated: its output up-axis is set to Y on glTF's convention rather than from a measured run — a wrong value there is invisible to every gate, volume and face count, and shows only as a model lying on its side in a viewer or slicer — and the azimuth its output frame puts the input photograph at is unset, so PROJECT_PHOTO_COLOUR falls back to recovering the pose from the silhouette for it. Neither affects a textured run.
