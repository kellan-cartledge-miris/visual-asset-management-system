Add-ons Overview

An add-on is an optional part of VAMS that ships with upstream VAMS, is maintained by upstream, and is off until a deployment enables it in configuration. Add-ons come in two kinds:

  • Integration with an external solution. The add-on connects VAMS to a solution that is deployed and run separately from VAMS. The add-on supplies the VAMS-side components that make VAMS work with that solution, or that extend the solution's functionality.
  • Stand-alone component. The add-on is a component that is not part of VAMS core and is not deployed externally. When the add-on is enabled, VAMS deploys every component of it.

An add-on is enabled through app.addons.* in the deployment configuration or, for a viewer, through the enabled flag of its entry in web/src/visualizerPlugin/config/addonViewerConfig.json.

Add-ons are different from custom code. Custom code is what an organization adds in its own fork of VAMS. Upstream ships every custom file empty and never edits it. An add-on is upstream code that upstream keeps working from release to release. The add-on files sit beside the core lists they extend, so add-on code stays off the path of core changes. Extending VAMS in a Fork lists the core, add-on and custom files list by list.

Adding an add-on to upstream VAMS​

An add-on contributed to upstream VAMS uses the add-on files: its routes in backend/backend/common/addonApiRoutes.py, its handlers and models in backend/backend/handlers/addon/ and backend/backend/models/addon/, its CDK resources in a nested stack under infra/lib/nestedStacks/addon/, its feature switch in infra/common/addonAppFeatures.ts, and its web, viewer and CLI entries in the add-on files listed in Extending VAMS in a Fork. Its configuration goes under app.addons and it is off by default. A feature that an organization adds only in its own fork uses the custom files instead.
